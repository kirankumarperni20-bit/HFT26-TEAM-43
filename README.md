# AI Research Assistant for Verifiable Summaries & Cross-Paper Synthesis

> **Project:** AI Research Assistant  
> **Architecture:** Modular Monolith  
> **Backend:** Python + FastAPI  
> **Frontend:** To be finalized by the frontend team  
> **LLM Provider:** Featherless AI  
> **Database:** PostgreSQL + pgvector (proposed)  
> **Team Size:** 4 Members

---

## 1. Project Overview

The AI Research Assistant helps users understand, compare, and verify information across multiple research papers.

Users can upload multiple research-paper PDFs, ask research questions, generate summaries, and compare findings across papers.

Unlike a conventional AI summarizer, this system follows a **Generator–Verifier architecture**.

The system does not simply generate an answer. It also:

1. Extracts relevant information from uploaded research papers.
2. Generates structured summaries and cross-paper comparisons.
3. Breaks generated content into independently verifiable atomic claims.
4. Retrieves relevant passages from the original research papers.
5. Classifies each claim as:
   - **Supported**
   - **Contradicted**
   - **Unresolved**
6. Provides exact evidence references so users can inspect the original source.

### Core principle

**Every factual claim generated by the system should be traceable to evidence in the uploaded research papers.**

## 2. System Architecture

We will follow a **Modular Monolith Architecture**.

This means we will have one backend application, but its internal responsibilities will be separated into independent modules.

We are not building separate microservices for each module because that would introduce unnecessary deployment, networking, and integration complexity for our current scope.

### High-level architecture

```text
                         USER
                           |
                           v
                    FRONTEND APPLICATION
                           |
                     REST API (HTTP)
                           |
                           v
                  FASTAPI BACKEND
                           |
          +----------------+----------------+
          |                |                |
          v                v                v
    INGESTION MODULE  GENAI MODULE    RETRIEVAL MODULE
          |                |                |
          |                |                |
          v                v                v
      PDF PARSER       FEATHERLESS       EMBEDDINGS
      TEXT EXTRACTION  LLM SERVICES      VECTOR SEARCH
      CHUNKING         SYNTHESIS          KEYWORD SEARCH
          |            CLAIMS             |
          |            VERIFICATION       |
          +----------------+---------------+
                           |
                           v
                       DATABASE
                           |
                 +---------+---------+
                 |                   |
                 v                   v
              DOCUMENTS            CHUNKS
              CLAIMS               EVIDENCE
              RESEARCH JOBS        VERIFICATIONS
                           |
                           v
                    STRUCTURED RESPONSE
                           |
                           v
                        FRONTEND
```

### Module responsibilities

| Module | Responsibility |
|---|---|
| Frontend | User interface, PDF uploads, research queries, summaries, comparisons, verification results |
| Ingestion | PDF processing, text extraction, paragraph reconstruction, chunking and source metadata |
| Retrieval | Embeddings, keyword search, vector search, hybrid retrieval and evidence retrieval |
| GenAI | Paper understanding, synthesis, claim decomposition and claim verification |
| Database | Persistent storage of documents, chunks, claims, evidence and research results |

**Important:** The modules communicate through agreed data contracts. They should not depend on another member's internal implementation.

## 3. Team Responsibilities

Each member owns a specific module. Members are free to choose their internal implementation, libraries and coding approach, provided that their module follows the shared contracts.

### Member 1 — PDF Ingestion & Document Processing

**Ownership:** `backend/ingestion/`

#### Responsibilities

- Implement PDF upload and validation.
- Extract text from PDFs using PyMuPDF or an equivalent library.
- Reconstruct paragraphs and preserve page information.
- Identify sections/headings wherever possible.
- Split extracted content into meaningful chunks.
- Generate stable document, paragraph and chunk IDs.
- Preserve the original extracted text.
- Store document metadata and extracted chunks.
- Track document processing status.

#### Expected output

The ingestion module must provide structured document and chunk data to the rest of the backend.

Example:

```json
{
  "paper_id": "P001",
  "filename": "research_paper.pdf",
  "status": "completed",
  "chunks": [
    {
      "chunk_id": "P001_C001",
      "paper_id": "P001",
      "page_number": 1,
      "paragraph_number": 2,
      "section": "Introduction",
      "text": "This research proposes a new approach..."
    },
    {
      "chunk_id": "P001_C002",
      "paper_id": "P001",
      "page_number": 5,
      "paragraph_number": 3,
      "section": "Results",
      "text": "The proposed model achieved an accuracy of..."
    }
  ]
}
```

#### Required contract

Every chunk must contain:

- `chunk_id`
- `paper_id`
- `page_number`
- `paragraph_number`
- `text`

`section` may be null if it cannot be identified.

#### Deliverable

A working ingestion module that accepts a PDF and produces traceable text chunks.

### Member 2 — Database, Embeddings & Retrieval

**Ownership:** `backend/retrieval/` and database integration.

#### Responsibilities

- Design database tables and relationships.
- Store documents and extracted chunks.
- Generate embeddings for chunks.
- Implement vector similarity search.
- Implement keyword-based retrieval (BM25 or equivalent).
- Implement hybrid retrieval if feasible.
- Retrieve relevant passages for individual claims.
- Return exact original text with source references.
- Rank retrieved evidence by relevance.

#### Expected input

The retrieval module receives an atomic claim.

Example:

```json
{
  "claim_id": "C001",
  "claim_text": "Paper A achieved 92% accuracy.",
  "paper_ids": ["P001", "P002"]
}
```

#### Expected output

```json
{
  "claim_id": "C001",
  "evidence": [
    {
      "evidence_id": "P001_C002",
      "chunk_id": "P001_C002",
      "paper_id": "P001",
      "page_number": 5,
      "paragraph_number": 3,
      "text": "The proposed model achieved an accuracy of 92%.",
      "retrieval_score": 0.91,
      "retrieval_method": "hybrid"
    }
  ]
}
```

#### Required contract

Every returned evidence passage must include:

- `evidence_id`
- `chunk_id`
- `paper_id`
- `page_number`
- `paragraph_number`
- `text`
- `retrieval_score`
- `retrieval_method`

The `text` field must contain the original stored passage, not an LLM-generated paraphrase.

#### Deliverable

A retrieval function that accepts a claim and returns ranked, traceable evidence passages.

### Member 3 — GenAI Engineer (User's Module)

**Ownership:** `backend/llm/`

#### Responsibilities

The GenAI module is responsible for understanding research papers, generating cross-paper synthesis and verifying generated claims.

It will communicate with Featherless AI through the backend.

#### Main components

**1. Paper Understanding**

- Receive extracted chunks from ingestion.
- Understand the paper's objective.
- Extract methodology.
- Identify datasets and evaluation metrics.
- Extract key findings.
- Identify limitations.
- Return structured JSON with source references.

**2. Cross-Paper Synthesis**

- Receive structured profiles of multiple papers.
- Compare methodologies, datasets, metrics and findings.
- Identify similarities and differences.
- Identify limitations and research gaps.
- Avoid comparing incompatible metrics as if they were equivalent.
- Avoid inventing information that is not present in the papers.

**3. Atomic Claim Decomposition**

- Break generated summaries into independently verifiable claims.
- Preserve the original generated text.
- Maintain each claim's position in the original output.
- Assign a unique claim ID.
- Avoid rewriting the original claim during decomposition.

Example:

```json
{
  "claims": [
    {
      "claim_id": "C001",
      "text": "Paper A uses Random Forest.",
      "start": 0,
      "end": 34
    },
    {
      "claim_id": "C002",
      "text": "Paper A achieved 92% accuracy.",
      "start": 39,
      "end": 71
    }
  ]
}
```

Offsets will use Unicode character positions, with the same convention documented for frontend highlighting.

**4. Claim Verification**

- Receive atomic claims.
- Request relevant evidence from the retrieval module.
- Send claims and retrieved evidence to the LLM.
- Classify claims as Supported, Contradicted or Unresolved.
- Return evidence IDs and a concise explanation.

Example:

```json
{
  "claim_id": "C002",
  "classification": "supported",
  "evidence_ids": ["P001_C002"],
  "justification": "The passage explicitly reports 92% accuracy."
}
```

**5. Python Validation**

The LLM output must never be trusted automatically.

Implement validation to check:

- Valid JSON structure.
- Valid classification values.
- Evidence IDs exist in the supplied evidence.
- Paper and chunk references are valid.
- Quoted text actually exists in the original stored passage.
- Required fields are present.

#### Important verification rules

| Situation | Classification |
|---|---|
| Evidence directly supports the claim | Supported |
| Evidence directly conflicts with the claim | Contradicted |
| Evidence is insufficient or unrelated | Unresolved |

A lack of supporting evidence does not automatically mean that a claim is contradicted.

#### Deliverable

A GenAI pipeline that accepts structured paper data, generates synthesis, decomposes claims and verifies those claims using retrieved evidence.

## 4. API Contracts — Important Integration Reference

This section defines how the frontend and backend communicate.

**All members must follow these endpoint names, HTTP methods and agreed request/response structures.**

The endpoints below are the proposed shared API contract. They should be implemented by the backend integrator and coordinated with the relevant module owners.

### A. Document APIs — Ingestion

| Method | Endpoint | Purpose | Owner |
|---|---|---|---|
| POST | `/api/documents/upload` | Upload one or more PDFs | Member 1 |
| GET | `/api/documents` | List uploaded papers | Backend integration |
| GET | `/api/documents/{paper_id}` | Get paper details | Backend integration |
| GET | `/api/documents/{paper_id}/status` | Get processing status | Member 1 |
| GET | `/api/documents/{paper_id}/chunks` | Retrieve extracted chunks | Member 1 |

#### Upload request

`POST /api/documents/upload`

Content type: `multipart/form-data`

Request:

```text
files: one or more PDF files
```

Example response:

```json
{
  "documents": [
    {
      "paper_id": "P001",
      "filename": "paper1.pdf",
      "status": "processing"
    }
  ]
}
```

The upload endpoint may return before extraction finishes. The frontend should check the document status endpoint.

Possible document statuses:

- `uploaded`
- `processing`
- `completed`
- `failed`

---

### B. Research APIs — Synthesis

| Method | Endpoint | Purpose | Owner |
|---|---|---|---|
| POST | `/api/research/generate` | Start summary/comparison generation | Member 3 + backend integration |
| GET | `/api/research/{research_id}` | Retrieve research results | Backend integration |
| GET | `/api/research/{research_id}/matrix` | Retrieve comparison matrix | Member 3 + backend integration |

#### Generate research request

`POST /api/research/generate`

```json
{
  "paper_ids": ["P001", "P002"],
  "question": "Compare the machine learning methods used in these papers.",
  "tasks": [
    "summarize",
    "compare"
  ]
}
```

Example response:

```json
{
  "research_id": "R001",
  "status": "processing",
  "message": "Research generation started."
}
```

The frontend should use `research_id` to retrieve the result.

Possible research statuses:

- `queued`
- `processing`
- `completed`
- `failed`

#### Research result response

`GET /api/research/{research_id}`

```json
{
  "research_id": "R001",
  "status": "completed",
  "summary": "The papers investigate different machine learning approaches...",
  "comparison": [
    {
      "aspect": "Methodology",
      "paper_comparisons": [
        {
          "paper_id": "P001",
          "value": "Random Forest"
        },
        {
          "paper_id": "P002",
          "value": "XGBoost"
        }
      ]
    }
  ],
  "claims": []
}
```

The `claims` field will contain the generated atomic claims and their verification results when verification is complete.

```text

unresolved
```

## 8. Important Technical Rules

These rules apply to all team members.

### Rule 1 — Do not change shared field names independently

For example, if the agreed field is:

```json
{
  "paper_id": "P001"
}
```

Do not independently rename it to:

```json
{
  "document_id": "P001"
}
```

If a change is necessary, discuss it with the team and update the shared contract.

### Rule 2 — Preserve source traceability

Every extracted chunk must have a stable reference.

Every evidence passage must refer to the original paper and source location.

Never use an LLM-generated paraphrase as if it were the original source text.

### Rule 3 — Keep the LLM API key private

Store credentials in `.env`.

```env
FEATHERLESS_API_KEY=your_api_key
FEATHERLESS_BASE_URL=your_base_url
FEATHERLESS_MODEL=your_model_name
```

Never commit `.env` to GitHub.

Add it to `.gitignore` and commit `.env.example` with placeholders only.

The frontend must never receive the API key.

### Rule 4 — Validate every LLM response

LLM output is untrusted input.

Use Pydantic or equivalent validation for JSON structures and Python checks for source references and evidence IDs.

### Rule 5 — Use asynchronous processing for long operations

PDF processing, embedding generation, synthesis and verification may take time.

Do not keep long-running HTTP requests open unnecessarily.

Return a job or research ID and allow the frontend to check its status.

### Rule 6 — Handle errors properly

Use a consistent error response:

```json
{
  "error": {
    "code": "DOCUMENT_PROCESSING_FAILED",
    "message": "Unable to process the uploaded PDF."
  }
}
```

Do not expose API keys, stack traces or internal credentials in API responses.

### Rule 7 — Keep modules independent

A member should be able to test their module without waiting for the entire application.

Use mock data and agreed schemas during development.

- Finalize endpoint names and request/response formats.

## 11. Testing & Evaluation

We should not evaluate the system only by whether its generated summary sounds correct.

The verification system must be evaluated against labelled examples.

Important evaluation criteria:

| Metric | What it measures |
|---|---|
| Claim-level precision | How many claims classified as supported are actually supported |
| Claim-level recall | How many genuinely supported claims were correctly identified |
| Source-link validity | Whether cited evidence points to the correct source |
| Quote validity | Whether the quoted passage exists in the original paper |
| Contradiction detection | Whether genuine conflicts are identified |
| Unresolved handling | Whether insufficient evidence is correctly labelled unresolved |

We must pay particular attention to **false-supported claims** because incorrectly presenting unsupported claims as verified undermines the entire purpose of the application.

## 13. Final Team Agreement

Before implementation, every member should understand the following:

1. Each member owns their assigned module.
2. Each module may have its own internal implementation.
3. Shared API contracts must remain consistent.
4. Data passed between modules must follow the agreed JSON schemas.
5. Source IDs and original text must be preserved.
6. LLM outputs must be validated before being returned.
7. Members should test modules independently before integration.
8. Any change to a shared contract must be communicated to the entire team.

### Our development principle

**Build independently. Communicate through contracts. Integrate systematically. Validate everything.**

The objective is not just to make four modules work individually. The objective is to make all four modules behave as one reliable application.
